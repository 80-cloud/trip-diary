## 1. 目的

公開 URL を開いた第三者が、**登録なしで 30 秒以内に主要機能を触れる**状態にする。

- 閲覧者は、アカウント登録の手間があるとその時点で離脱しやすい。
- 空のデータベースや、コメントが 1 件も付いていない一覧では、交流機能の多さが伝わらない。
- 公開環境は **月額 0 円** で維持できる構成にする (AWS 構成は 2026-05-19 に撤収済み)。

## 5. ゲストログイン設計 (F-GUEST-01)

### 5-1. 方式比較

| 観点 | A. 共有の固定デモアカウント (review-board 方式) | B. 訪問者ごとの一時ゲスト (採用) |
|---|---|---|
| 他の閲覧者の影響 | 受ける (誰かが投稿を消すと次の人は空の画面を見る) | 受けない |
| パスワード | フロントのコードに埋め込む必要がある | 不要 (サーバー側で発行) |
| 入った直後の通知 | 最初から未読がある | そのままでは 0 件 → §5-2 の初回通知で補う |
| 後片付け | 定期的な初期化の仕組みが必要 | 期限切れゲストを削除するだけ |
| 実装量 | 小 | 中 |

### 5-2. 仕様

- **API**: `POST /api/v1/guest_login`
  - ゲストユーザーを新規作成し、通常ログインと同じ HttpOnly Cookie を発行して `201` を返す。
  - メールアドレスは `guest-<ランダム値>@example.invalid` (`.invalid` は実在しないことが保証されたドメイン)。パスワードはランダム値で、利用者には返さない。
  - 表示名は `ゲスト-<4 桁>`。
- **DB**: `users.guest` (boolean, 既定 false, NOT NULL, index あり) を追加する。
- **有効期限**: 作成から 24 時間 (Cookie の有効期限と同じ)。
- **初回通知**: ゲスト作成時に、デモユーザー 2 名がゲストをフォローする。フォロー作成時の既存フックで通知が 2 件でき、ヘッダーのベルに未読バッジが付く。デモデータ (§6) が無い環境では何もしない。
- **後片付け**: ゲストログインのたびに、作成から 24 時間を過ぎたゲストを最大 20 件ずつ削除する。削除は ActiveRecord の `destroy` 経由とし、関連データ (投稿・コメント・いいね・フォロー・通知・画像) も一緒に消す。手動用に `script/cleanup_guest_users.rb` (`bin/rails runner` 経由・既存の `script/cleanup_test_users.rb` と同じ形) も用意する。定期実行の仕組みを持たない無料構成でも片付けが進む。
- **ゲストの制限**
  - ゲストが作る旅行記録の公開範囲は **private (自分のみ)** に固定する。他の閲覧者に内容が見えない。
  - 画像アップロードは 1 ゲストあたり合計 5 枚まで (保存容量の無料枠を守る)。
  - コメント・いいね・フォロー・お気に入りは通常どおり可能。24 時間で消える。
- **ゲストの行動の見え方** (次の閲覧者に匿名の書き込みやゲスト名を見せない)
  - コメント: ゲストが書いたコメントは、そのゲスト本人にだけ返す。コメント件数も、本人以外にはゲスト分を除いた値を返す。`comments_count` は counter cache でゲスト分も数えるため、そのままの値を返すと一覧の件数と表示件数が食い違う (CLAUDE.md §12-5)。
  - フォロー一覧: デモユーザーの「フォロー中」「フォロワー」一覧とその件数に、ゲストを含めない (ゲスト本人が自分の一覧を見る場合を除く)。初回通知のフォロー (§5-2) は残るが、他の閲覧者には見えない。
  - いいね: 画面に出るのは件数だけで、誰が押したかの一覧は無い。件数に含まれるのは 24 時間以内なので許容する。
  - 通知: ゲストの行動による通知はデモユーザー宛てに作られるが、デモユーザーは誰もログインできないため他の閲覧者の目に触れない。
- **濫用対策**
  - IP 単位の回数制限: 10 分に 5 回まで (rack-attack。P0-10 と合わせて公開先で効くことを確認する)。
  - 有効なゲストが 200 人を超えたら新規発行を止め、`503` と「現在混み合っています」を返す。
- **画面**
  - ログイン画面と未ログイン時のヘッダーに「ゲストとして試す (登録不要)」ボタンを置く。
  - ゲスト中はヘッダー下に「ゲストモード: 24 時間後にデータは削除されます」と表示する。
  - ボタンは `type="button"`、非同期処理はハンドラ関数の中で例外を処理する (CLAUDE.md §12-3 / §12-7)。
  - ログイン画面のメールアドレス・パスワードの初期値を空にする (P0-4)。
  - ゲスト中は旅行作成・編集フォームの公開範囲の欄に「ゲストの記録は自分だけに表示されます」と表示する (選んだ値と保存結果が違うことを事前に伝える)。

### 5-3. 受け入れ条件

- Given 未ログイン / When `POST /api/v1/guest_login` / Then `201`・Cookie 発行・`guest: true` のユーザーが 1 件増える
- Given デモデータ投入済み / When ゲストログイン / Then そのゲスト宛ての未読通知が 2 件ある
- Given ゲストでログイン中 / When 公開範囲 `public` で旅行記録を作る / Then 公開範囲は `private` で保存される
- Given ゲストが 5 枚アップロード済み / When 6 枚目を送る / Then `422` と上限のメッセージ
- Given 作成から 24 時間を過ぎたゲスト / When 別の訪問者がゲストログイン / Then 期限切れゲストと関連データが削除される (孤立レコード 0 件)
- Given 有効なゲストが 200 人 / When ゲストログイン / Then `503` と混雑メッセージ
- Given ゲストでログイン中 / When 他人の旅行記録の本人専用セクション (予算・メモ等) を取得 / Then 通常ユーザーと同じく見えない (件数などの派生値も含む。CLAUDE.md §12-5)
- Given ログイン画面 / When 「ゲストとして試す」を押す / Then トップへ遷移し、ゲスト表示と通知バッジが出る
- Given ゲストがデモ旅行にコメント済み / When 未ログインで同じ旅行の詳細と一覧を取得 / Then ゲストのコメントは返らず、コメント件数もゲスト分を除いた値
- Given ゲストの初回通知でデモユーザーがゲストをフォロー済み / When 未ログインでそのデモユーザーのフォロー中一覧を取得 / Then ゲストは含まれず、件数もゲスト分を除いた値

### 5-4. セキュリティ確認

- 既存の対策 (E-H1 汎用エラー / E-H2 応答時間の平準化 / E-M2 ログアウト時のトークン無効化) を壊さない。
- ゲストの権限は通常ユーザー以下。今後管理系の操作を追加する場合はゲストを除外する。
- `docs/セキュリティ自己監査.md` にゲスト関連の確認項目を追記する。
- 他人のメールアドレスを返さない (P0-7)。ゲストやデモユーザーの架空のアドレスも同じ扱いにする。E-H1 / E-H2 で「アドレスが登録済みか」を推測させないようにしているため、一覧 API からアドレスそのものが読めると対策の意味が無くなる。

### 5-5. 公開環境でのサインアップ停止 (P0-9)

公開環境はゲストのみとし、実在のメールアドレスを受け取らない。ゲストは 24 時間で消えるため、保存期間の問題も生じない。

- **API**: 環境変数 `SIGNUP_ENABLED` で切り替える。development と test は既定で有効、公開環境では `false` にする。無効のとき `POST /api/v1/signup` は `403` と汎用メッセージを返し、理由の詳細は返さない (E-H1 と同じ考え方)。
- **画面**: `NUXT_PUBLIC_SIGNUP_ENABLED` で、サインアップへのリンク・ボタンを出し分ける。`/signup` に直接来た場合はログイン画面へ案内する。画面を隠すだけでは API を直接呼べるため、API 側の停止を必須とする。
- **E2E**: E2E のテストはサインアップ API でテスト用ユーザーを作っている (`e2e/fixtures/auth-state.js`)。CI では `SIGNUP_ENABLED` を有効のままにする。
- **受け入れ条件**
  - Given `SIGNUP_ENABLED` が無効 / When `POST /api/v1/signup` / Then `403`・ユーザーは増えない・Cookie は発行されない
  - Given `SIGNUP_ENABLED` が有効 (既定) / When 正しい入力で `POST /api/v1/signup` / Then 従来どおり `201`
  - Given 画面側の切り替えが無効 / When ログイン画面・ヘッダーを表示 / Then サインアップへの導線が無い

## 8. 公開環境の無料構成案 (P1-1)

| 役割 | 候補 | 無料枠の要点 | 確認方法 |
|---|---|---|---|
| アプリ (Rails + ビルド済み Nuxt) | Render Free | 0.15 CPU / 512 MB (2026-10-01 に管理画面で確認。当初の 0.1 CPU は読み違い)。月 750 時間。15 分アクセスが無いと停止し、復帰に約 1 分。アジアの地域はシンガポールだけ。外向きの帯域はワークスペース全体で月 5 GB | 公式ドキュメント |
| DB | TiDB Cloud Starter | MySQL 互換。1 インスタンスあたり月 5 GiB・5,000 万 RU。同時接続 400。本番用は Singapore に作る (Render と同じ地域に置くため)。東京のインスタンスは試し用に残す | 公式ドキュメント・作成画面 |
| 画像 | Cloudinary Free | 月 25 クレジット。1 ファイル 10 MB (画像・その他とも)・画像 25 MP。クレジットカード不要 | 公式ドキュメント・管理画面 (2026-09-30) |

- **同一オリジン配信**: Cookie が `SameSite=Lax` のため、Nuxt のビルド結果を Rails から配信し、画面と API を同じオリジンにする。
- **画面の配り方とポート (2026-09-30・#145)**
  - 本番用イメージは、Node の段で `nuxt generate` した画面を含む。JS と CSS (`_nuxt`) は `public` に、画面のひな形 (`index.html`) は `public` の外の `frontend_shell` に置き、Rails の `FrontendController` が `Cache-Control: no-cache` を付けて返す。`public` のファイルは 1 年キャッシュされるため、ひな形を置くと公開し直しても古い画面が読まれ続ける。
  - `/api`・`/rails` (画像の配信)・`/up` と、拡張子の付いた URL は横取りしない。
  - ビルドの文脈はリポジトリの直下にする。Render では Dockerfile Path を `backend/Dockerfile`、Docker build context directory を `.` にする。Render はサービスの環境変数をビルド引数として渡すが、Dockerfile で `ARG` にしているのは画面の 2 つの値とバージョンだけなので、秘密の値はビルドに入らない。
  - thrust が `HTTP_PORT` (10000) で受け、Puma を `TARGET_PORT` (3001) で起動する (イメージの既定値)。thrust は Puma の `PORT` を `TARGET_PORT` の値で上書きするため、Render が渡す `PORT` (10000) とぶつからない。
  - Render のヘルスチェックのパスは `/up` にする (2xx か 3xx を 5 秒以内に返せば正常とみなされる)。
  - 手元でイメージを `PORT=10000` だけで起動し、画面の URL を直接開く・再読み込みする・API・ヘルスチェックが期待どおり返ることを確かめた。
- **画面の切り替えはビルド時に決まる**: 画面は `nuxt generate` で作った静的ファイルを配るため、`NUXT_PUBLIC_SIGNUP_ENABLED` は Nuxt のビルド時に渡す (実行時の環境変数は効かない)。Rails の `SIGNUP_ENABLED` とは別の変数なので両方を `false` にし、公開後に `POST /api/v1/signup` が `403` を返すことと、画面にサインアップの導線が無いことを確かめる (#122)。
- **メモリ実測**: 本番用イメージを 512 MB / 0.1 CPU に制限して起動した結果、アイドル 113 MiB・30 リクエスト後 129 MiB・メモリ不足による停止なし・全件 `200` (平均 0.58 秒)。起動は 89 秒 (うち約 15 秒は S3 の認証情報を探す待ち)。S3 をやめたあと (#149) のイメージでは、同じ制限で起動は 69 秒 (DB の作成とマイグレーションを含む)・起動直後 128 MiB だった。公開環境 (Render Free) ではメモリと CPU が見られない (Application Metrics は有料のプランだけ) ため、手元の測定で代える。#156 のあとのイメージは、同じ制限で起動 80 秒・202 MiB だった。Render の Deploy started から live までは約 1 分だった。
- **本番用 DB の整理 (2026-09-30・#146 で実施)**: 本番設定にあったキャッシュ・ジョブ・WebSocket 用の DB 3 つをやめ、アプリ本体の DB 1 つにまとめた。
  - キャッシュ (回数制限に使う) とジョブ (画像削除 P0-11 に使う) のテーブルは、Solid Queue の README にある 1 つの DB で使うときの手順に沿って、schema ファイルの中身を普通のマイグレーションに写して作る。
  - WebSocket (ActionCable) はチャンネルが無いため、本番でも DB を使わない `async` にした。
  - 本番の DB は、起動時の `db:prepare` が `database.yml` の照合順序 (`utf8mb4_unicode_ci`) で作る。DB を新しく作ったときは `db:seed` も流れるが、`seeds.rb` は development 以外では何もしないため、公開前に `RAILS_ENV=production` が入っていることを確かめる。
  - 手元でイメージを起動し、作られる DB が 1 つだけであること・2 回目の起動で DB を作らないこと・キャッシュの読み書き・ジョブの登録・ログインの回数制限 (6 回目で `429`) を確かめた。TiDB の試し用の DB でも、マイグレーション (外部キーを含む) とテストが通った。
- **ジョブの実行場所**: Render Free には常駐ワーカーが無いため、`SOLID_QUEUE_IN_PUMA=1` でアプリ本体の中でジョブを動かす (P0-11)。
  - TiDB は `FOR UPDATE SKIP LOCKED` を受け付けるが対応しておらず、鍵をかけない読み取りになる。主キーを取り出さない形では、実行計画を組む段階で「列が見つからない」というエラーになる (TiDB の開発元の PR pingcap/tidb#69782)。公開環境に最初に出したとき (2026-10-01)、主キーを取り出さない Dispatcher (予約されたジョブを配る係) がこのエラーで落ち、作り直されるのをくり返した。手元の MySQL と CI では起きない。
  - 本番の設定で `config.solid_queue.use_skip_locked = false` にし、普通の `FOR UPDATE` を使う (#156)。Worker と Dispatcher は 1 つずつなので、待ち合いはほとんど起きない。試し用の TiDB で、Solid Queue の 4 つの処理 (配る・取る・blocked の解放・プロセスの後片付け) が通ることを確かめた。
  - 見回りの間隔 (2026-10-04・#165): 本番だけ、Worker を 2 秒・Dispatcher を 5 秒にした (`config/queue.yml` の production。手元と CI は 0.1 秒・1 秒のまま)。公開した直後、帯域が 1 日約 170 MB の勢いで増え、月末に 5 GB を超える見込みだった。ほとんどがアプリから外への通信 (Service-Initiated) で、起きている 1 時間あたり約 25 MB だった。手元で本番用イメージを 512 MB / 0.1 CPU で何もせずに 5 分動かすと、送信は 0.1 秒・1 秒で約 26 MB/時、2 秒・5 秒で約 2 MB/時 (92% 減) だった。動くジョブは画像の削除と解析・毎時の後片付けだけなので、数秒の遅れは困らない。修正後の帯域は 1 日約 22 MB だった (2026-10-05)。
- **訪問者の IP (2026-10-01・#151・#158・P0-10)**: 回数制限は Rack の `req.ip` で訪問者の IP を決める。
  - Render の記事は「アプリは既定では中継の IP を見る。回数制限は `x-forwarded-for` から訪問者の IP を読む」としている。
  - 公開環境の `X-Forwarded-For` は「訪問者が送った値, 本当の訪問者, Cloudflare, Render 内部」の並びだった。Render は届いた値を消さず、後ろに足す。
  - #151 では、Render の担当者の回答 (2021 年) をもとに先頭を訪問者とみなした (`TRUST_FIRST_FORWARDED_IP=1`)。公開環境で先頭を毎回偽ると制限をすり抜けられると分かり、廃止した (#158)。
  - Rack の `req.ip` は、末尾から見て「信頼する中継」でない最初の IP を選ぶ。既定ではプライベートの IP だけを信頼するので、Cloudflare が公開している IP の範囲 (cloudflare.com/ips-v4・ips-v6) を足した。左側の値を偽っても選ばれない。範囲はコードに持つので、変わったら書き直す。公開環境のログに出た中継の IP が、この範囲に入ることを確かめた。
  - Rack は既定で `X-Forwarded-For` より先に `Forwarded` ヘッダーを読み、これも偽れるため、`X-Forwarded-For` だけを読むようにした。
  - 公開のときに、`X-Forwarded-For` と `Forwarded` を毎回変えて偽って送っても 6 回目が `429` になることと、2 つの回線から別々に数えられることを確かめる。
- **画像の置き場 (2026-09-30・#149)**: 公開環境の Active Storage の保存先を Cloudinary Free にした。
  - 当初の候補の Cloudflare R2 は、支払い方法の登録が要るかを公式の文書から読み取れなかった。Cloudinary は料金ページに「クレジットカード不要」とある。
  - 本番は `storage.yml` の `cloudinary` (`folder: trip-diary`) を使う。接続情報は環境変数 `CLOUDINARY_URL` を gem が読む。gem は読み込むと保存名の作り方を差し替えるため、production のグループだけに入れ、開発とテストは Disk のままにした。
  - 無料アカウントは PDF の配信が既定で止められているため、管理画面の Security で許可した (チケットは PDF を受け付ける)。
  - 画像の URL は今までどおり `rails_blob_path` で作り、アプリのリダイレクトで Cloudinary の配信 URL に移る。gem の注意書きに従い、変換 (variant) は使わない。
  - 無料プランの上限は管理画面 (Settings → Account) で確認した (2026-09-30): 画像とその他のファイルは 1 つ 10 MB まで・画像は 25 MP まで・環境は 1 つ。アプリの上限 (写真 5 MB・アバター 2 MB・チケット 10 MB) はこの中に収まる。
  - 手元で本番用イメージを 512 MB / 0.1 CPU で起動し、写真・28.5 MP の写真・10 MB ちょうどの PDF・アバターが保存・配信されることを確かめた。変換をしないため、画像 25 MP の上限は当たらなかった。画面から写真を上げると、切り抜き枠の初期値が元の画像の 80% のため、この写真は 18.3 MP になった。
  - 旅行の削除と、期限切れゲストの削除のどちらでも、ジョブで Cloudinary からも消えることを確かめた (P0-11 の手元での確認)。ただし、配信済みのコピーは CDN に最大 30 日残りうる (公式ドキュメント)。扱いは [セキュリティ自己監査.md](./セキュリティ自己監査.md) に書いた。
  - 環境が 1 つなので、手元の確認で上げたファイルも公開環境と同じ場所に入る。確認のあとは消す。
- **支払い方法の確認結果 (2026-09-27・公式ドキュメント)**

- **Render の設定 (2026-10-01 に設定した。今の値は [インフラ構成.md](./インフラ構成.md) §0-2)**
  - ビルドの分数: Hobby のワークスペースは、ビルドが月 500 分まで。支払い方法が無いと、使い切った時点で月末までワークスペースの新しいビルドが止まる (公式ドキュメント)。公式の文書は新しいビルドが止まることだけを書いており、動いているサービスについては書いていない (ビルドはサービスとは別の資源で動く、とはある)。

  - 1 回のビルド時間は、1 回目が 3 分 9 秒・2 回目からは 1 分弱だった。月 500 分の枠に対して十分に小さい。
  - DB の許可リスト: 本番用の TiDB の許可リストに、Render の管理画面 (Connect → Outbound) に出るシンガポールの送信元の範囲 2 つ (`74.220.52.0/24`・`74.220.60.0/24`) と、`demo:seed` を流す手元の IP だけを入れ、作成時の全許可の規則は消した。規則の名前に使えるのは英数字と `_` だけ。この範囲は同じ地域の Render の全サービスで共通 (公式ドキュメント) なので、許可リストだけではこのアプリからの接続に絞れない。守りの中心は TLS (`verify_identity`) と強いパスワードにする。

### 8-1. 停止からの復帰と死活監視 (P1-2 / P1-6)

Render Free は 15 分アクセスが無いと停止し、復帰に約 1 分かかる。

| 案 | 月の稼働時間 | 評価 |
|---|---|---|
| 15 分未満の間隔で常に起こしておく | 約 744 時間 (24 時間 × 31 日) | 採用しない。無料枠 750 時間をほぼ使い切り、同じワークスペースで別の無料サービスを動かすと、全部が月の途中で止まる。利用規約の「利用制限を回避しない」に当たると読まれる恐れもある (§8) |
| 1 時間ごとの死活監視 | 約 200 時間 (見積もり。実測は 1 日約 8 時間で、月に約 240 時間。訪問と確認の作業を含む。2026-10-05) | 起こしたままにはできないが、壊れていれば気づける |

- **通常時 (2026-10-01・#153)**: `.github/workflows/uptime.yml` が毎時 17 分に動き、`/api/v1/health` の `status` が `ok` であることと、DB を読む `/api/v1/trips` が `200` を返すことを確かめる (公開リポジトリのため無料)。
  - GitHub の定期実行は毎時 0 分ごろが混み、遅れや取りこぼしがあるため、17 分にした (公式ドキュメント)。
  - 定期実行はベストエフォートとして扱う。公式ドキュメントに "High load times include the start of every hour." "some queued jobs may be dropped." とある。2026-10-01 は、`UPTIME_URL` を入れてから 8 時間で 2 回だった (予定から 2〜6 時間遅れ・どちらも成功)。
  - 2026-10-02〜10-04 (UTC) の実測: 1 日 4〜5 回 (平均 4.7 回)・失敗 0 件・間隔 3〜7 時間 (平均約 5 時間)。予定の毎時 17 分から 1〜55 分ずれ、ほとんどの回が落とされる。壊れてから気づくまで、最大 7 時間ほどかかりうる。
  - Render Free は停止から起きるまで約 1 分かかるため、1 回 90 秒まで待ち、4 回まで繰り返す。JSON の `status` まで見るので、起動中の画面を正常と取り違えない。
  - 公開 URL はリポジトリの変数 `UPTIME_URL` (Settings → Secrets and variables → Actions → Variables) に入れる。秘密の値ではない。変数が無いあいだはジョブを飛ばす。
  - 失敗するとジョブが失敗になり、GitHub の通知 (メール) が、ワークフローの cron の行を最後に変えた人に届く (公式ドキュメント)。外部の監視サービスは使わない。公開のときに、わざと違う URL にして知らせが届くことを確かめる。
- **運用**: 監視の 3 本・月 1 回見るもの (60 日ルールを含む)・障害のときの手順・デプロイされないときの見方は、[ログ・監視・障害対応設計書.md](./ログ・監視・障害対応設計書.md) §7 にまとめた。
- **README**: 「最初の表示に 1 分ほどかかることがある」と明記し、冒頭にスクリーンショットを置く (P1-2。#126 で対応)。
- **採用しなかった候補**
  - AWS の継続: ロードバランサー・コンテナ・DB で月数十ドル。RDS の MySQL 8.0 は 2026-08-01 から延長サポート料金の対象。
  - Oracle Always Free: 7 日間 CPU・ネットワーク・メモリの使用率がすべて 20% 未満だと回収される。アクセスの少ない公開デモとは相性が悪い。
