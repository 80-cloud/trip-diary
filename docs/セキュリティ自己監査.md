## §3 trip-diary 実施結果

### E-H1: signup の field-level エラー漏洩 — 🔴 **要修正 (PR #8 で fix)**

- **症状**: `backend/app/controllers/api/v1/auth_controller.rb:10` で `render json: { errors: user.errors.full_messages }` をそのまま返却 → email uniqueness エラー時に「Email has already been taken」が露出
- **攻撃シナリオ**: 任意の email で signup 試行 → 「Email has already been taken」を観測 = 登録済み判定
- **修正方針**: signup 失敗時はフィールド名なしの汎用文言 `{ error: "入力内容に誤りがあります..." }` 統一返却。422 ステータスは維持
- **回帰テスト**: `auth_controller_test.rb` で「email 重複時と password 短すぎ時のレスポンスボディが完全一致」を assert

### E-H2: login timing attack — 🔴 **要修正 (PR #8 で fix)**

- **症状**: `auth_controller.rb:14-22` で `User.find_by` 後 `user&.authenticate` のため、email 不在時は bcrypt 計算をスキップ → 応答時間で email 存在性が漏れる
- **修正方針**: email 不在時にも **同じ cost** のダミー bcrypt を実行する。`DUMMY_DIGEST = BCrypt::Password.create("dummy", cost: BCrypt::Engine.cost).to_s.freeze` を定数化し、boot 時に 1 回のみ生成
- **回帰テスト**: 不在 email と存在 email (誤 password) のログイン応答時間差が **200ms 以内** であることを assert

### E-H3: dev seed の本番漏洩 — 🟡 **OK (docs 強化のみ)**

- **現状**: `backend/db/seeds.rb:1` `return unless Rails.env.development?` で本番ガード済 ✅
- **残リスク**: `.env.example` に `RAILS_ENV=development` がそのまま記載 → EC2 で `.env.example` をリネーム運用すると development のまま起動 → seed が動く
- **PR #8 での対応**:
  - `.env.example` の該当行直上にコメント追加
  - README に本番デプロイ前チェックリスト 4 項目を追加 (2026-09-28 に [インフラ構成.md](./インフラ構成.md) §5-1 へ移した)
- **デモデータ (Issue #117)**: 公開環境にも入れるデモデータ (`demo:seed` / `demo:reset`) は、production では `DEMO_SEED_CONFIRM=1` が無いと `DemoSeeder::NotConfirmed` で止まる。`demo:reset` もデモユーザーを消す前に止まる。デモユーザーのパスワードはランダム値を作って捨てるため、誰もログインできない

### E-H4: 公開 API による他人のメールアドレスの返却 — 🔴 **要修正 (Issue #107 で fix)**

- **発見日**: 2026-09-27 (公開デモ化に向けた点検)
- **現象**: 未ログインで取得できる旅行一覧・旅行詳細 (投稿者・コメント投稿者)・タグ別一覧・フォロー一覧と、ログイン中のお気に入り一覧が、他人の `email` を返していた (5 コントローラー)
- **影響**: 登録済みの全利用者のメールアドレスを、未ログインのまま収集できる。E-H1 / E-H2 の列挙対策が意味を失う
- **修正**: 他人の情報を返す payload から `email` を削除。フロントエンドは他人の `email` を使っていない
- **回帰テスト**: `privacy_test.rb` がレスポンスの入れ子をすべてたどり、`email` キーが無いことを確認する。`/me` が本人の `email` を返すことも確認する (削除しすぎの防止)

### E-M3 横展開: 人気タグとタグ別ページの件数 — 🔴 **要修正 (Issue #107 で fix)**

- **現象**: `tags.trips_count` (counter cache) は非公開・下書きの旅行も数える。人気タグにこの値を使っていたため、本人にしか見えない旅行のタグ名や件数 0 のタグがトップページに出ていた。タグ別ページの件数も一覧と食い違っていた
- **修正**: 人気タグは公開済みの旅行だけを JOIN して数える。タグ別ページの件数は一覧と同じ「見える旅行」で数える。`tag_summary` は件数を呼び出し側から必ず渡す形にし、counter cache の値を返さない
- **回帰テスト**: `privacy_test.rb` (人気タグに非公開・下書きのタグが出ない / タグ別ページの件数が一覧の件数と一致する)

### F-GUEST-01: ゲストログインの確認項目 — ✅ **OK (Issue #109 / #111 / #113 で対応・一部は後続)**

- **対象**: 登録せずに試せる一時ゲスト (`POST /api/v1/guest_login`)。公開デモ化計画書 §5-4 の確認項目
- **既存の対策を壊さない**: E-H1 (汎用エラー) / E-H2 (応答時間の平準化) / E-M2 (ログアウト時のトークン無効化) の回帰テストがすべて成功
- **実在の個人情報を持たない**: アドレスは `@example.invalid` (実在しないことが保証されたドメイン)。パスワードは乱数で、利用者に返さない。`guest_login` の応答は本人の情報だけで、他人の `email` を含まない (E-H4)
- **権限は通常ユーザー以下**: ゲストの旅行記録は作成・更新とも private に固定する。モデルの `before_validation` で行うので、保存の経路によらず効く
- **濫用対策**: IP ごとに 10 分 5 回まで (rack-attack)。有効なゲストが 200 人に達したら `503` と汎用メッセージを返す
- **後片付け**: 作成から 24 時間を過ぎたゲストを `destroy` で削除し、関連データも一緒に消す。孤立レコード 0 件を回帰テストで確認
- **ゲストの行動を他の閲覧者に見せない**: ゲストのコメントはそのゲスト本人にだけ返し、コメント件数も同じ条件で数える (一覧・詳細・タグ別一覧・お気に入り一覧で一致。E-M3 の横展開)。フォロー一覧からゲストを除き、本人が見る場合だけ残す
- **公開環境のサインアップ停止**: `SIGNUP_ENABLED=false` のとき `signup` は `403` と汎用メッセージを返し、ユーザーも Cookie も作らない。ゲストログインは影響を受けない (画面側の出し分けは #123)
- **保存容量の上限**: ゲストの画像は旅行の画像・チケットのファイル・アバターを合わせて 5 枚まで。検査はモデルで行うので、保存の経路によらず効く。チケットの削除がコールバックを通らず添付ファイルが残っていた (作成と削除の繰り返しで上限をすり抜けられた) ため、`destroy` 経由に直した
- **後続で対応**: プロキシの内側での IP 判定 (P0-10)
- **回帰テスト**: `guest_login_test.rb` (11 件) / `user_guest_test.rb` (5 件) / `guest_visibility_test.rb` (6 件) / `signup_switch_test.rb` (3 件) / `guest_image_limit_test.rb` (5 件)

### E-M6: 横展開チェック (comment / like 削除の冪等性・認可) — ✅ **OK**

### E-L5: signup の race condition — 🟡 **軽微 (Phase 2 残課題)**

- model validation + DB UNIQUE index あり (`create_users.rb:11`)
- ただし check→save 間で `ActiveRecord::RecordNotUnique` raise の可能性 → 現状 `application_controller.rb` の `rescue_from` 対象外のため 500 が出うる
- Phase 2: `ApplicationController` に `rescue_from ActiveRecord::RecordNotUnique` を追加し 422 で返却

### E-PWReset: パスワードリセット — ❌ **未実装 (Phase 2 着手時の Definition of Ready)**

- 現状: 未実装 (`backend/config/application.rb:10` で `action_mailer/railtie` がコメントアウト)
- **Phase 2 実装時の 5 原則を本書に固定** (sns-board の自己監査の追補から流用):
  1. メール送信エンドポイントは存在 email でも不在 email でも **200 統一** (列挙防止)
  2. 同じく **レイテンシも統一** (常に enqueue まで実行 / 不在ならスキップだが sleep でフェイク)
  3. **トークンは SHA-256 ハッシュで保存** (raw 値は URL のみ / DB は hash)
  4. **消費エンドポイント** (パスワード再設定) も成功/失敗で文言・status を統一
  5. 上記 4 点それぞれに **回帰テストを書く**

### E-Proc: Issue/PR テンプレのセキュリティチェック項目化 — ❌ **PR #8 で対応**
