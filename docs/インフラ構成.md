## 0. 今の公開構成 (2026-10〜: Render・TiDB Cloud Starter・Cloudinary)

> 公開デモ (https://trip-diary-wpaf.onrender.com) を月額 0 円で動かす今の構成です (#155)。構成を選んだ理由と調べた経緯は [公開デモ化計画書.md](./公開デモ化計画書.md) §8、監視と障害のときの手順は [ログ・監視・障害対応設計書.md](./ログ・監視・障害対応設計書.md) にあります。
> §2〜§5 は 2026-05 の AWS 構成の記録です。infra/ の Terraform のコードとほかの docs が §2〜§5 の番号を参照しているため、番号を変えずにこの節を先頭に置きました。

### 0-1. 構成図

```
訪問者のブラウザ
  │ HTTPS
  ▼
Cloudflare (Render の前段。こちらでは設定しない)
  │
  ▼
Render の Web Service (Docker・Singapore・Free)
  └ Thruster (ポート 10000)
      └ Puma (ポート 3001)
          ├ Rails API (/api/v1/*) とヘルスチェック (/up)
          ├ ビルド済みの画面 (nuxt generate の結果を Rails が返す)
          └ Solid Queue (SOLID_QUEUE_IN_PUMA=1 で Puma の中で動く)
  │                                     │
  │ MySQL プロトコル + TLS               │ HTTPS
  ▼                                     ▼
TiDB Cloud Starter (Singapore)        Cloudinary Free
  DB は trip_diary_production 1 つ      フォルダは trip-diary/
  (アプリ・キャッシュ・ジョブ)           (写真・アバター・チケット)

GitHub Actions
  ├ CI と E2E (成功した commit だけを Render がデプロイする)
  └ Uptime (毎時。/api/v1/health と /api/v1/trips を見る)
```

- 画面と API を同じオリジンから配る (Cookie が `SameSite=Lax` のため)。CORS の設定は要らない
- Render Free には常駐のワーカーが無いため、ジョブ (画像の削除など) は Puma の中で動かす。Render が止まっているあいだはジョブも止まる

### 0-2. 各サービスの設定

| サービス | 項目 | 値 |
|---|---|---|
| Render | プランと地域 | Free・Singapore (アジアで選べる地域はここだけ) |
| Render | 資源 | 512 MB・0.15 CPU。15 分アクセスが無いと止まり、次のアクセスで約 1 分かけて起きる |
| Render | ビルド | Dockerfile Path は `backend/Dockerfile`、文脈 (Docker build context directory) はリポジトリの直下 `.` |
| Render | ヘルスチェック | `/up` (2xx か 3xx を 5 秒以内に返せば正常) |
| Render | Auto-Deploy | After CI Checks Pass |
| Render | Build Filters | 含める: `backend/**`・`frontend/**`・`.dockerignore` / 除く: `backend/test/**`・`frontend/tests/**`・`**/*.md` (docs とテストだけの変更ではビルドしない) |
| Render | 環境変数 (11 個) | `DB_HOST`・`MYSQL_PORT`・`MYSQL_USER`・`MYSQL_PASSWORD`・`MYSQL_DATABASE`・`MYSQL_SSL_MODE` (`verify_identity`)・`SIGNUP_ENABLED` (`false`)・`SOLID_QUEUE_IN_PUMA` (`1`)・`SECRET_KEY_BASE`・`JWT_SECRET`・`CLOUDINARY_URL`。値は Render の画面にだけ置く |
| Render | 入れない環境変数 | `WEB_CONCURRENCY` (Render が既定で 1 を入れる。2 以上にすると回数制限の記録が worker ごとに分かれ、メモリも足りない)・`RAILS_MASTER_KEY` (credentials を使わない)・`RAILS_ENV` (イメージの既定が production)・`S3_*`・`CORS_ORIGINS` |
| TiDB Cloud | プランと地域 | Starter・Singapore (Render と同じ地域)・Spending Limit は $0 |
| TiDB Cloud | 接続 | TLS が必須 (`MYSQL_SSL_MODE=verify_identity`)・ポート 4000 |
| TiDB Cloud | 許可リスト | Render の送信元の範囲 2 つ (`74.220.52.0/24`・`74.220.60.0/24`。Render の Connect → Outbound に出る) と、`demo:seed` などを流す手元の IP だけ。全許可の規則は消した。規則の名前に使えるのは英数字と `_` だけ |
| TiDB Cloud | DB の作成 | 起動時の `db:prepare` が `database.yml` の照合順序 (`utf8mb4_unicode_ci`) で作る (TiDB の既定は `utf8mb4_bin`) |
| Cloudinary | プラン | Free・環境は 1 つ (手元の確認で上げたファイルも同じ場所に入るので、確認のあとは消す) |
| Cloudinary | 保存先 | `storage.yml` の `cloudinary` (`folder: trip-diary`)。接続情報は `CLOUDINARY_URL` を gem が読む |
| Cloudinary | API キー | 公開環境専用のキーを作った。役割は Master Admin (無料プランで選べるのは Master Admin と Media Library User の 2 つだけ) |
| Cloudinary | PDF の配信 | 無料アカウントでは既定で止まっているため、管理画面の Security で許可した。アカウントを作り直したら、許可し直さないとチケットの PDF が開けない |
| Cloudinary | 保存の形 | PDF も `resource_type` は image (format が pdf) になる。変換 (variant) は使わない |

- Render の送信元の範囲は、同じ地域の Render の全サービスで共通。許可リストだけではこのアプリからの接続に絞れないので、守りの中心は TLS (`verify_identity`) と強いパスワードにする
- TiDB の無料のバックアップ (毎日・保持 1 日・新しいインスタンスへの復元だけ) には頼らない。デモは `demo:reset` と `demo:seed` で作り直せる。ゲストのデータは 24 時間で消えるので守る対象にしない

### 0-3. デプロイの流れ

```
PR を main にマージする (Squash and merge)
  │
  ▼
GitHub Actions: CI (backend・frontend・security) と E2E
  │ すべて成功 (Render は success・neutral・skipped を合格とみなす)
  ▼
Render: Build Filters に当たる変更があればビルドを始める (docs だけなら何もしない)
  │ Docker のビルド (1 回目は 3 分 9 秒・2 回目からは 1 分弱)
  ▼
起動: bin/docker-entrypoint が db:prepare (マイグレーション) → thrust → Puma
  │ /up が正常を返したら切り替える (Deploy started から live まで約 1 分)
  ▼
Live (ビルドや起動が失敗したときは、前の版が動き続ける)
```

- チェックが 1 つでも失敗か取り消しだと、自動デプロイしない (Render の公式ドキュメント)。毎時の Uptime の結果も main の最新の commit に付くので、これも含まれる
- 急ぐときや、CI を再実行して通したときは、Render の Manual Deploy → Deploy latest commit で出す
- commit メッセージでデプロイを止める書き方は使わない (squash のマージでは、1 つの commit に書くだけでマージのデプロイ全体が止まる)

### 0-4. 費用が 0 円である根拠

| サービス | 根拠 |
|---|---|
| Render | Free で、支払い方法を登録していない。無料枠 (月 750 時間はワークスペース単位・ビルドは月 500 分) を超えると、請求ではなくサービスやビルドが止まる |
| TiDB Cloud | Starter で Spending Limit が $0、カードも登録していない。無料枠 (月 5 GiB・5,000 万 RU) を使い切ると、請求ではなく新しい接続を拒否する。予算の知らせ (Budgets) は Spending Limit が 0 より大きいときだけ作られるので、知らせのメールは来ない (使用量は手で見る) |
| Cloudinary | Free で、カードは不要。月 25 クレジット |
| GitHub Actions | 公開リポジトリなので無料 |

### 0-5. 公開環境のチェックリスト (デプロイや設定を変える前)

- [ ] Render に `RAILS_ENV` を入れていない (イメージの既定が production。[セキュリティ自己監査.md](./セキュリティ自己監査.md) E-H3)
- [ ] `SECRET_KEY_BASE` と `JWT_SECRET` は `openssl rand -hex 64` で作った公開環境専用の値 (Render の Generate は 128 ビットなので使わない)
- [ ] `SIGNUP_ENABLED=false` (Rails) と、ビルド引数 `NUXT_PUBLIC_SIGNUP_ENABLED=false` (Dockerfile の既定) の両方が効いている。公開後に `POST /api/v1/signup` が 403 になる
- [ ] `MYSQL_SSL_MODE=verify_identity` が入っている
- [ ] TiDB の許可リストに全許可 (`0.0.0.0/0`) の規則が無い
- [ ] `CLOUDINARY_URL` は公開環境専用のキー (キーの末尾だけを確かめ、値は画面に出さない)
- [ ] `db:seed` は流れても何もしない (`seeds.rb` は development だけ)。デモデータは手元から `demo:seed` で入れる ([公開デモ化計画書.md](./公開デモ化計画書.md) §6-1)
- [ ] 手元から公開環境の DB につなぐときは `TZ=UTC` を付ける (`default_timezone` が `:local` のため、付けないと 9 時間ずれて読み書きされる)
- [ ] マージしたら、Render の Events で Deploy started から live まで進んだかを見る

### 2-2. AWS リソース (Terraform で IaC 化 / `infra/*.tf`)

| リソース | スペック | 月額目安 | 備考 |

### 2-3. デプロイフロー (sns-board (非公開) のデプロイ用スクリプトを流用)

```
[backend (Rails)]                          [frontend (Nuxt SPA)]
git commit                                 git commit
    │                                          │
    ▼ scripts/deploy-backend.sh                ▼ scripts/deploy-frontend.sh
docker buildx --platform linux/amd64       npm run generate
    │                                          │
    ▼ aws ecr push (tag=git SHA)               ▼ aws s3 sync .output/public s3://...
terraform apply -var backend_image_tag=...     │
    │ (Task Def 更新)                          ▼ aws cloudfront create-invalidation /index.html
    ▼
aws ecs update-service --force-new-deployment
    │
    ▼ wait services-stable (rolling update)
```

> **重要**: image tag は必ず git commit SHA (`latest` 禁止)。mutable tag を本番に誤投入する事故防止 ([docs/セキュリティ自己監査.md](./セキュリティ自己監査.md) E-H3 と同型のリスク)。

### 2-4. セキュリティ・運用

| 項目 | 方針 |
|---|---|
| 通信 | 全リスナー HTTPS only (ACM / ALB は HTTP → HTTPS リダイレクト) |
| DB アクセス | RDS SG は ECS task SG からのみ 3306 許可 |
| 機密情報 | SSM Parameter Store (SecureString / KMS 暗号化) / 静的 AWS キー不要 (IAM Role 経由) |
| 画像 IAM | task_role に `s3:PutObject` / `GetObject` / `DeleteObject` を uploads bucket スコープで付与 |
| バックアップ | RDS 自動スナップショット (7 日保持) / S3 versioning は Phase B 検討 |
| ログ | Rails STDOUT → CloudWatch Logs (awslogs ドライバ) |
| 監視 | CloudWatch アラーム (CPU > 80% / 5xx 急増 / RDS IOPS) は **Phase B** で導入 |
| デプロイ | image tag = git SHA / 鍵類は SSM 経由 / `terraform plan` は人間目視必須 (CLAUDE.md §6) |

## 5. 過去の本番構成 (2026-05) の運用手順とチェックリスト

### 5-1. 本番デプロイ前チェックリスト

> 今の公開環境 (Render) のチェックリストは §0-5 にあります。以下は 2026-05 の AWS 構成のときのものです。

#### Phase 2 までに定めたもの

- [ ] `RAILS_ENV=production` で起動する (development のままだと `seeds.rb` が本番 DB を汚す。詳細は [セキュリティ自己監査.md](./セキュリティ自己監査.md) §3 E-H3)

### 5-2. 利用パターンと月額の目安

常時公開しない前提で、使うときだけ構築し、終わったら撤収してコストを抑えていた。

| パターン | 月の稼働時間 | 月額 | 用途 |
|---|---|---|---|
| 24 時間稼働 | 720h | 約 $30 | 継続して公開する期間 |
| 1 日 3 時間 | 90h | 約 $4 | デモの準備と公開 |
| 月 30 時間 | 30h | 約 $1.2 | 公開前のリハーサル |
| 0 時間 (撤収後) | 0h | $0.5 未満 | tfstate のバケットと Budgets の通知だけが残る |

公開する期間が決まっているなら、前日に構築し、終わったら撤収するのが最も安い。

### 5-3. 初回の構築 (デプロイ)

事前準備 (一度だけ): tfstate 用の S3 バケット `trip-diary-tfstate` を ap-northeast-1 に手動で作る。バージョニング・パブリックアクセスのブロック・AES256 の暗号化を有効にする ([infra/versions.tf](../infra/versions.tf) の冒頭のコメントも参照)。

```bash
cp infra/terraform.tfvars.example infra/terraform.tfvars
chmod 600 infra/terraform.tfvars
cd infra
terraform init
terraform plan
terraform apply
cd ..
./scripts/deploy-backend.sh
./scripts/deploy-frontend.sh
terraform -chdir=infra output cloudfront_domain_name
```

- `terraform.tfvars` の `REPLACE_WITH_*` をすべて実際の値にする (db_password / rails_master_key / secret_key_base / jwt_secret / s3_bucket_name / budget_notification_email)。機密ファイルなので `chmod 600` で本人だけが読めるようにする
- `terraform plan` では 63 個のリソースが作られる予定であることを目で確かめる。`terraform apply` は y/n の確認に yes と答える (自動承認は使わない。CLAUDE.md §6)。所要 15〜20 分 (CloudFront だけで約 10 分)
- `deploy-backend.sh` はイメージの push と ECS のローリング更新、`deploy-frontend.sh` は Nuxt の静的ファイルを S3 と CloudFront に配る
- 最後に出るドメインをブラウザで開く。CloudFront の反映に 5〜15 分かかることがあるので、初回に 5xx が出たら待つ
- 構築の 5〜30 分後に AWS Budgets の確認メールが届く。リンクを押して confirm しないと、月次の通知が届かない

### 5-4. 緊急停止 (Fargate の課金だけを止め、構成は残す)

```bash
aws ecs update-service --cluster trip-diary-cluster --service trip-diary-backend --desired-count 0 --region ap-northeast-1
```

- 戻すときは `--desired-count 1` にする (起動に約 3 分)
- 減るのは Fargate Spot の分 (月 $3〜9) だけで、ALB ($18) と RDS の課金は続く

### 5-5. 撤収 (すべてのリソースを取り壊す)

```bash
./scripts/teardown.sh --dry-run
./scripts/teardown.sh
```

- `--dry-run` で、撤収の計画だけを先に表示する
- 本番の撤収では、プロジェクト名と yes の 2 段階の入力を求められる
- 撤収後に ECS・ALB・RDS・CloudFront が残っていないかは、スクリプトの中で自動で確かめる
- 投稿された旅行・画像・ユーザーはすべて消える (RDS と S3 の uploads が中身ごと消える)。デモデータが必要なら、構築し直したあとに投入し直す

### 5-6. 撤収後も残るもの

| 残るリソース | 対処 |
|---|---|
| `trip-diary-tfstate` の S3 バケット | 次の構築で使うので残す。完全に消すなら AWS のコンソールで手動 |
| AWS Budgets (月次 $30 の通知) | 通知先のメールが残る。不要ならコンソールの Budgets で削除 |
| SNS のサブスクリプション (Budgets の通知) | 同上 |
| Route53 のホストゾーン | この構成では作っていない (独自ドメインを使う場合のみ) |
| CloudWatch のロググループ | 保持期間 7 日で自然に消える |

### 5-7. 鍵類の保護

- `infra/terraform.tfvars` はすべてのシークレット (DB のパスワード / Rails の master key / JWT の secret など) を含むので、`chmod 600` で本人だけが読めるようにする (`ls -la` で `-rw-------` になっていること)
- 撤収後は、tfvars の `db_password` / `secret_key_base` / `jwt_secret` / `rails_master_key` を破棄する (構築し直すときは作り直す)。SSM Parameter Store の SecureString は撤収で消える
- tfvars を残したい場合は、機密の値をパスワードマネージャに移し、手元の tfvars は消す
