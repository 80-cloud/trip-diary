## 1. プロジェクト概要

### 1-1. 背景・課題

作者 (hideharu-AI) は、これまで
**タスク管理アプリ (task-board)** → **レシピ管理アプリ (recipe-board)** → **SNS 風アプリ (sns-board、非公開)** と段階的に題材を変えてフルスタック開発を経験してきた。

4 つ目の題材として、**旅行の記録を時系列で残し、複数ユーザーが互いの旅行記録に対してコメント・いいねで反応できる「旅行記録アプリ (trip-diary)」** を選定。
1 ユーザー1記録の閉じた CRUD ではなく、**マルチユーザー双方向インタラクション**を扱う点が、sns-board から引き続き取り組むテーマとなる。

### 1-2. 目的 (学習到達点)

本プロジェクトの学習姿勢は「**習う → 慣れる → マスター**」の3段階で進める。

| 段階 | 姿勢 | 目安 |
|---|---|---|
| 第 1 段階 (習う) | 公式チュートリアル・参考プロジェクト (recipe-board / sns-board) を写経・模倣しながら最低限の動作原理を理解する | Phase 1 立ち上げ初期 |
| 第 2 段階 (慣れる) | 完璧を求めず手を動かし、一連の流れ (DB → API → UI → デプロイ) を体感する。動くものを作ることを最優先 | Phase 1 〜 Phase 2 |
| 第 3 段階 (マスター) | 各機能の設計判断・トレードオフを言語化し、他人にレビューできる水準まで深掘る | Phase 3 〜完了後 |

> **「習うより慣れろ」段階では完璧主義で手が止まることを避ける。**
> 「マスター」段階では「なぜこの設計か」「他の選択肢はあったか」「どこに事故の芽があるか」を自分の言葉で説明できることを目標とする。

詳細は [学習ロードマップ.md](./学習ロードマップ.md) を参照。

#### 学習対象 (到達点の具体)

- マルチユーザー前提のドメイン設計を経験する (他者のコメント・いいねを想定)
- 1 対多 (Trip → DayEntry) のネスト構造を扱う (recipe-board の「材料・手順」を発展)
- 認証 (JWT in HttpOnly Cookie) と認可 (自分の記録のみ編集・削除可) を実装する
- 画像アップロード (Phase1: ローカルディスク / Phase3: S3) を扱う
- 非正規化カウンタ (いいね数 / コメント数) の同期の難しさを学ぶ
- AWS 無料枠での本番デプロイを経験する (Phase3)

### 1-3. 対象ユーザー

- 個人開発のアプリだが **マルチユーザー前提**で設計
- 公開デモでは、だれでもゲストとして登録せずに試せる (ゲストのデータは 24 時間で削除・同時に有効なゲストは 200 人まで)
- 公開環境では通常のサインアップを止める (実在のメールアドレスを保存しないため。コードとテストは残す)

## 2. 用語定義

| 用語 | 定義 |
|---|---|
| 旅行記録 (Trip) | 1 回の旅行を表すルートエンティティ。タイトル・期間・場所・本文を持つ |
| 出来事 (DayEntry) | 旅行中の 1 日 (または 1 シーン) のメモ。Trip に複数ぶら下がる (recipe-board の「材料・手順」相当のネスト) |
| 公開範囲 | 旅行記録の閲覧可否制御。`public` / `friends` / `private` (Phase2 で導入) |
| いいね (Like) | 旅行記録に対する 1 ユーザー 1 回の反応 |
| コメント (Comment) | 旅行記録に対するテキスト反応 (140 文字以内) |
| 投稿者 | 旅行記録を作成したユーザー (User) |

## 4. 非機能要件

### 4-1. 性能

| 項目 | 目標値 |
|---|---|
| 一覧画面 初回表示 | 2 秒以内 (ローカル開発環境) |
| 詳細画面 表示 | 1 秒以内 |
| 同時接続数 | 5〜10 ユーザー (学習用想定) |

### 4-2. セキュリティ

- パスワードは BCrypt でハッシュ化 (Rails `has_secure_password`)
- 認証は JWT in **HttpOnly + Secure (本番) + SameSite=Lax** Cookie で保持 (XSS による窃取耐性)
- CSRF: SPA + JWT Cookie 構成のため、`SameSite=Lax` と HttpOnly の Cookie で基本を守る。状態変更系 API に独自ヘッダ (`X-CSRF-Token` 等) を足す方式は、今は入れていない (判断と理由は [セキュリティ自己監査.md](./セキュリティ自己監査.md) §5 の E-CSRF)
- UGC (本文・コメント) は Rails 側でサニタイズ (HTML タグはエスケープ表示)
- 画像アップロードは MIME / 拡張子 / サイズ (5MB) 制限
- 機密情報 (`.env` / SECRET_KEY_BASE / JWT_SECRET) は **絶対にコミットしない**

### 4-3. 可用性・運用

- Phase 1〜2 はローカル開発のみ
- Phase 3 で AWS にデプロイした (2026-05)。バックアップは RDS の自動スナップショット (7 日間保持) だった
- 2026-10〜 の公開環境は、TiDB Cloud Starter の無料のバックアップ (毎日・保持 1 日) に頼らない。デモは `demo:reset` と `demo:seed` で作り直し、ゲストのデータは 24 時間で消える ([インフラ構成.md](./インフラ構成.md) §0-2)
- 監視と障害のときの手順は [ログ・監視・障害対応設計書.md](./ログ・監視・障害対応設計書.md) §7 にまとめた

### 4-4. 拡張性

- API は `/api/v1/` で名前空間を切り、将来的な v2 移行を想定
- フロントエンドは Nuxt の Pinia ストアで状態管理し、画面追加を容易にする
- 画像保存先は ActiveStorage で抽象化し、保存先の切替を設定 1 つで行えるようにする (手元とテストは Disk・2026-05 の本番は S3・2026-10〜 の公開環境は Cloudinary)

### 4-5. アクセシビリティ

- フォームには `<label>` を必ず付与し、`for` と `id` で入力欄とつなぐ
- アイコンだけのボタン・リンクには `aria-label` で名前を付ける。狭い幅で文字を隠すときも、名前は変えない
- 文字と背景の比は WCAG 2.1 AA の 4.5:1 以上にする (#177)。基準に届かない色の組み合わせは、`frontend/tests/style/contrast.test.js` で見つける
- 色だけに依存した情報表現を避ける (アイコン併用)

## 5. 技術スタック (サマリ)

詳細は [技術スタック.md](./技術スタック.md) を参照。

| レイヤー | 採用技術 | 採用理由 |
|---|---|---|
| バックエンド | Ruby 3.4.9 / Rails 8.1 (API モード) | recipe-board での実績があり、API モードで画面と分けて作れるため |
| フロントエンド | Nuxt 4 + Vue 3 (**TypeScript 不採用 = 純 JS**) | 学習負荷を抑え、習う→慣れるに集中するため |
| DB | MySQL 8 (Docker) | recipe-board と同構成 |
| 認証 | JWT in HttpOnly Cookie | sns-board の方式を踏襲 |
| 画像 | ActiveStorage (手元: Disk / 公開環境: Cloudinary。2026-05 の本番は S3) | Rails 標準で実装容易。保存先は設定で切り替える |

## 9. リスク・前提

| # | リスク / 前提 | 対策 |
|---|---|---|
| R-01 | TypeScript 不採用のため大規模化で型不整合バグが増える可能性 | Phase4 以降で TS 化を検討。Phase1〜3 は規模を抑える |
| R-02 | 画像アップロードを Disk で行うとサーバーの容量を圧迫する | 2026-05 の本番は S3、2026-10〜 の公開環境は Cloudinary に置く。ゲストの画像は合計 5 枚まで・24 時間で消す |
| R-03 | コメント・いいねの非正規化カウンタが本数とズレる可能性 | `counter_cache` (`likes_count`・`comments_count`) だけで保つ。月次の再計算は今は行わない。ずれを見つけたら Issue にし、Rails の `reset_counters` で直す |
| R-04 | 公開環境ではサインアップを止め、ゲストログインで試してもらうため、新規登録 UI の安全対策 (bot 対策・メール確認) は入れていない | サインアップを公開する場合は reCAPTCHA / メール確認を追加する |
| R-05 | Phase 1 で MVP まで一気に実装するため、認可漏れの検証が薄くなる | Phase 2 冒頭で認可テストを整備した ([セキュリティ自己監査.md](./セキュリティ自己監査.md)) |
| R-06 | 公開環境は無料枠で動かすため、上限 (Render の稼働時間と帯域・TiDB の RU・Cloudinary のクレジット) を超えると、月末まで止まるか接続を拒否される | 月 1 回使用量を見る ([ログ・監視・障害対応設計書.md](./ログ・監視・障害対応設計書.md) §7-3)。支払い方法を登録しないので、請求にはならない |
